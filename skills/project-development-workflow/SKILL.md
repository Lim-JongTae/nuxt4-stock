# 프로젝트 개발 작업 방식

## 사용 시점

다음 작업을 수행할 때 이 스킬을 사용한다.

- 이 저장소의 기능 추가, 버그 수정, 리팩터링, UI 변경
- LS증권 Open API 데이터 수집·가공·표시 로직 변경
- 주식 분석 결과, 보고서, 스크리너 또는 보유·관심종목 기능 변경
- 여러 파일을 조사하고 구현한 뒤 테스트와 실행 검증이 필요한 작업

단순한 사실 확인이나 한 줄짜리 오탈자 수정에는 전체 절차를 적용하지 않고 필요한 단계만 수행한다.

## 기본 원칙

1. 사용자의 최신 요청과 저장소의 `CLAUDE.md`를 최우선으로 따른다.
2. 기존 코드와 패턴을 먼저 읽고, 필요한 범위만 수정한다.
3. 전용 파일 도구(`Glob`, `Grep`, `Read`, `Edit`, `Write`)를 우선 사용한다.
4. 서로 독립적인 탐색과 검증은 병렬로 수행한다.
5. 사용자의 기존 변경 사항을 덮어쓰거나 되돌리지 않는다.
6. 확인하지 못한 동작을 성공했다고 보고하지 않는다.
7. 코드 주석은 동작 설명이 아니라 비자명한 제약이나 이유를 설명할 때만 추가한다.
8. 모든 사용자 커뮤니케이션은 한국어로 작성하고, 코드 식별자와 기술 용어는 원문을 유지한다.

## 표준 작업 흐름

### 1. 요구사항과 범위 확인

- 사용자의 목표, 성공 조건, 영향 범위를 한 문장으로 정리한다.
- 구현이 필요한 요청이면 먼저 변경 전에 현재 상태와 관련 파일을 조사한다.
- 선택지가 여러 개이고 결과에 큰 차이가 있으면 구현 전에 질문하거나 계획을 제시한다.
- 단순하고 명확한 수정은 불필요한 계획 단계 없이 진행한다.

### 2. 저장소 탐색

다음 순서로 필요한 맥락을 수집한다.

1. `CLAUDE.md`와 관련 하위 지침 확인
2. `git status`로 기존 변경 사항 확인
3. 대상 파일과 호출부를 `Glob`·`Grep`으로 찾기
4. 대상 파일 전체 또는 충분한 관련 범위를 `Read`로 확인
5. 타입, Store, Composable, API 경계와 테스트 위치 확인

기존 변경 사항이 대상 파일에 있으면 해당 변경을 보존하면서 현재 코드와 함께 이해한다. 관련 없는 변경은 건드리지 않는다.

### 3. 구현

- 기존 구조와 네이밍, 상태 관리 방식을 따른다.
- 요구사항에 직접 필요한 파일만 수정한다.
- 새로운 추상화, 기능 플래그, 호환성 우회, 임시 하드코딩을 추가하지 않는다.
- 외부 입력과 API 경계에서는 필요한 검증을 수행한다.
- 오류가 발생하면 가짜 데이터나 임의의 기본값으로 대체하지 말고 실패 원인을 보존하여 표시한다.
- 타입 정의는 프로젝트 루트 `utils/types/`에 중앙 집중하고 필요한 곳에서 import한다.
- UI 변경은 기존 디자인과 반응형 동작을 유지하며, 사용자가 실제로 수행할 수 있는 상태와 오류 상태를 함께 고려한다.

### 4. 검증

변경 위험도에 맞춰 다음을 수행한다.

- 정적 확인: 타입 오류, lint, import 누락, 사용하지 않는 코드
- 기능 테스트: 관련 단위·통합 테스트 또는 프로젝트의 기존 검증 명령
- UI 변경: 개발 서버를 시작하고 브라우저에서 정상 경로와 주요 경계 상태를 직접 확인
- API 변경: 성공 응답, 빈 응답, 통신 실패, 잘못된 데이터 형태를 확인
- 변경 후 `git diff`로 의도하지 않은 변경과 민감정보 포함 여부를 확인

검증을 실행할 수 없는 경우 이유와 남은 위험을 명확히 보고한다.

### 5. 마무리

- 변경 파일과 핵심 동작을 짧게 요약한다.
- 실행한 검증과 결과를 기록한다.
- 커밋은 사용자가 명시적으로 요청한 경우에만 만든다.
- 커밋 요청을 받으면 먼저 `git status`, staged·unstaged `git diff`, 최근 `git log`를 확인한다.
- 특정 파일만 명시적으로 stage하고, 기존 커밋을 amend하지 않으며, hook을 우회하지 않는다.
- push, PR 생성, 외부 시스템 변경은 명시적 요청 없이는 수행하지 않는다.

## 주식 데이터 작업 규칙

이 프로젝트의 주식 시세와 분석 데이터에는 다음 규칙을 반드시 적용한다.

- 모든 시세, 종가, 공매도, 분석 수치는 LS증권 Open API의 동적 응답만 사용한다.
- 주식 시세 및 종가 조회는 LS증권 `t1305` 기간별주가 TR을 사용하고 `exchgubun: "U"` 통합시세를 적용한다.
- API 키와 비밀키는 `.env`에서만 읽고 코드에 노출하거나 기록하지 않는다.
- API 통신 또는 자료 수집 실패 시 가짜 데이터, 임시 보정값, 하드코딩된 대체 수치를 만들지 않는다. 붉은색 오류 상태와 원인을 표시한다.
- 최초 진입과 새로고침 시 Store와 LocalStorage의 데이터 흐름을 확인하고, 기존 보존 정책을 깨지 않는다.
- Pinia Store를 화면의 우선 데이터 원천으로 사용하며, 외부 API 호출은 새로고침이나 명시적인 정밀 분석 요청에 맞춰 수행한다.
- 계산과 분석은 Composable 또는 기존 비즈니스 로직 계층에서 수행하고 UI에 중복 계산을 두지 않는다.
- 보고서 생성 시 `종목.md`의 분류를 정확히 따른다. 보유종목은 `holdings`, 관심종목은 `watchlist`로 기록한다.
- 보고서 파일은 `report/YYYY-MM-DD.json`, 차트 이미지는 `report/images/YYYY-MM-DD/[종목명].png` 규칙을 따른다.
- LS증권에서 수집한 분석 내용은 보고서에서 `LS증권`으로 표시한다.
- 이동평균선, 거래량, RSI, 볼린저 밴드, 변동성 등 기존 프로젝트가 요구하는 지표를 누락하지 않으며, 데이터가 부족하면 판단을 단정하지 않는다.
- 증감 수치의 텍스트 색상은 양수 붉은색, 음수 푸른색, 보합 하늘색 규칙을 따른다.
- 주식 분석 보고서는 투자 조언의 불확실성과 데이터 시점을 명시하고, 손실을 보장하는 표현을 사용하지 않는다.

## 보고서·분석 작업

주식 정보를 분석하거나 보고서를 생성할 때는 프로젝트에 등록된 `finance-helper` 계열 report 스킬을 우선 확인하고 사용한다. LS증권 API 가이드가 필요한데 `report/LS증권API가이드.md`가 없을 때만 공식 가이드를 학습하여 해당 파일에 저장한다.

분석 결과를 작성하기 전에 다음을 확인한다.

- 분석 기준일과 데이터 수집 시각
- 종목 분류와 보유 수량·평균단가 적용 여부
- 원시 데이터가 실제 API 응답인지 여부
- 기술적 지표 계산에 필요한 기간이 충분한지 여부
- 누락·실패 데이터와 판단의 한계

## 사용자 업데이트 형식

작업 중에는 다음 시점에 짧게 알린다.

- 무엇을 조사하는지 시작 시
- 중요한 코드 구조나 문제를 발견했을 때
- 구현 방향이 바뀌거나 막힌 경우
- 검증을 시작하고 결과가 나온 경우

최종 응답은 변경 내용, 검증 결과, 미실행 항목만 간결하게 포함한다. 사용자가 요청하지 않은 장황한 튜토리얼이나 커밋을 추가하지 않는다.
