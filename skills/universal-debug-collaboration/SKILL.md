# 범용 디버깅 및 협업 작업 방식

## 사용 시점

다음 작업에 이 스킬을 사용한다.

- 새 기능 구현 중 발생한 오류 조사
- 기존 코드의 버그 재현과 원인 분석
- 테스트 실패, 타입 오류, 빌드 오류, 런타임 오류 해결
- API·데이터·상태·UI 문제의 단계별 진단
- 여러 파일에 걸친 수정 후 회귀(regression) 검증
- 사용자와 로그와 진행 상황을 공유하며 함께 문제를 해결하는 작업

## 핵심 원칙

1. **재현 후 수정한다.** 오류 메시지만 보고 추측으로 코드를 변경하지 않는다.
2. **원인을 먼저 좁힌다.** 증상과 원인을 구분하고, 확인된 사실과 가설을 분리한다.
3. **최소 범위만 수정한다.** 오류 해결에 직접 필요한 코드만 변경한다.
4. **수정 전후를 비교한다.** 변경으로 해결된 문제와 새로 생긴 문제를 모두 검증한다.
5. **사용자에게 숨기지 않는다.** 막힘, 불확실성, 검증 실패, 남은 위험을 즉시 알린다.
6. **로그는 안전하고 제거 가능하게 만든다.** 민감정보를 출력하지 않으며, 임시 로그는 검증 후 제거하거나 명확히 관리한다.
7. **한 번에 한 가지 가설을 검증한다.** 여러 원인을 동시에 바꾸면 어떤 변경이 효과가 있었는지 알 수 없다.
8. **기존 동작을 보존한다.** 관련 없는 리팩터링이나 예방적 수정으로 문제 범위를 넓히지 않는다.
9. **실패를 성공으로 포장하지 않는다.** 실행하지 못한 검증은 통과한 것으로 보고하지 않는다.
10. **모든 사용자 커뮤니케이션은 한국어로 한다.** 코드 식별자와 오류 메시지는 원문을 유지한다.

## 표준 디버깅 절차

### 1. 문제를 명확히 정의한다

먼저 다음 항목을 기록하거나 사용자에게 확인한다.

- 기대한 동작
- 실제로 발생한 동작
- 재현 조건과 재현 빈도
- 오류가 처음 발생한 시점 또는 변경 사항
- 오류 메시지와 stack trace 전체
- 영향을 받는 환경, 입력, 브라우저, OS 또는 실행 명령
- 성공을 판단할 기준

불명확한 요구사항이 핵심 원인이라면 구현보다 먼저 질문한다.

### 2. 작업 공간을 보호한다

- 수정 전에 현재 Git 상태와 사용자의 미완성 변경 사항을 확인한다.
- 사용자가 만든 변경 사항을 삭제하거나 덮어쓰지 않는다.
- 대상 파일의 현재 내용을 읽고 주변 호출부와 테스트를 확인한다.
- 관련 없는 파일은 조사하거나 수정하지 않는다.
- 오류를 없애기 위해 `reset --hard`, 강제 checkout, 파일 삭제, hook 우회 같은 파괴적 방법을 사용하지 않는다.

### 3. 재현한다

가능한 가장 작은 재현 절차를 만든다.

1. 오류가 발생하는 명령 또는 UI 경로를 실행한다.
2. 입력과 환경을 고정한다.
3. stdout, stderr, 브라우저 console, 네트워크 응답, stack trace를 수집한다.
4. 오류가 매번 발생하는지 확인한다.
5. 재현되지 않으면 추측으로 수정하지 말고 관찰 가능한 추가 정보와 로그를 요청한다.

재현 절차는 다른 사람이 그대로 실행할 수 있을 정도로 구체적으로 기록한다.

### 4. 원인을 좁힌다

다음 순서로 범위를 줄인다.

1. **경계 확인:** 입력, API 응답, 파일, 환경 변수, 사용자 이벤트
2. **변환 확인:** parsing, mapping, filtering, 계산, 직렬화
3. **상태 확인:** Store, cache, local state, 비동기 순서, stale data
4. **출력 확인:** 렌더링, DOM, 응답 코드, 저장 결과
5. **회귀 확인:** 최근 diff, 호출부, 타입 계약, 관련 테스트

필요하면 binary search 방식으로 최근 변경이나 데이터 경계를 단계적으로 분리한다. 원인을 설명할 때는 다음 형식을 사용한다.

### 5. 진단 로그를 추가한다

로그는 문제를 관찰하기 위한 최소한의 구조화된 정보를 포함한다.

```ts
console.debug('[debug] loadItems:start', {
  itemCount: items.length,
  requestId,
})

console.debug('[debug] loadItems:response', {
  status: response.status,
  resultCount: result.length,
})
```

로그 작성 규칙:

- 고정된 접두사와 단계명을 사용한다. 예: `[debug] feature:phase`
- 시작, 입력 요약, 외부 호출, 변환 결과, 종료 또는 실패 지점을 구분한다.
- 배열 전체나 대용량 payload 대신 길이, ID, 상태 코드, 필드 존재 여부를 기록한다.
- 토큰, 비밀번호, API key, cookie, session 값, 개인정보, 전체 인증 헤더를 절대 출력하지 않는다.
- 민감할 수 있는 값은 마스킹하거나 존재 여부만 기록한다.
- 반복 호출되는 경로에서는 로그 폭주를 방지한다.
- 예외는 원래 오류 객체와 context를 함께 기록하되 민감한 요청·응답 본문은 필터링한다.
- 디버깅 목적이 끝나면 임시 로그를 제거한다. 운영에 필요한 로그라면 프로젝트의 logging 정책에 맞게 수준을 조정한다.

### 6. 최소 수정으로 해결한다

- 발견된 원인과 직접 연결된 코드만 수정한다.
- 변수명 변경, 대규모 리팩터링, 의존성 교체를 오류 해결과 함께 진행하지 않는다.
- `try/catch`로 오류를 숨기거나 무조건적인 fallback, 임의의 기본값, 빈 배열 반환으로 증상을 감추지 않는다.
- 데이터가 없거나 API가 실패한 경우 호출자가 오류를 구분할 수 있도록 기존 오류 흐름을 보존한다.
- 타입 오류는 `as any`, 무분별한 non-null assertion, 비활성화 주석으로 우회하지 않는다.
- 비동기 문제는 임의의 `setTimeout`이나 retry 추가로 덮지 말고 순서·취소·중복 실행의 원인을 확인한다.
- 수정이 다른 모듈의 계약을 바꿀 경우 호출부와 테스트를 함께 확인한다.

### 7. 단계적으로 검증한다

수정 후 아래 순서로 검증한다.

1. 동일한 재현 절차를 다시 실행한다.
2. 원래 오류가 사라졌는지 확인한다.
3. 수정한 함수 또는 모듈의 정상 입력을 검증한다.
4. 빈 값, 경계값, 잘못된 입력, 네트워크 실패 등 관련 실패 경로를 검증한다.
5. 수정한 코드의 호출부와 의존 기능을 검증한다.
6. 타입 검사, lint, 단위 테스트, 통합 테스트, 빌드를 실행한다.
7. UI 변경이면 실제 개발 서버와 브라우저에서 정상 경로와 오류 상태를 확인한다.
8. 임시 로그가 남아 있는지와 민감정보가 출력되지 않는지 확인한다.
9. `git diff`로 의도하지 않은 변경과 회귀 가능성을 검토한다.

검증 중 새 오류가 발생하면 원래 문제와 분리하여 기록한다. 한 문제를 해결하기 위해 생긴 새 문제를 원래 성공으로 간주하지 않는다.

## 여러 오류를 다루는 방법

오류가 여러 개이면 다음 기준으로 분리한다.

- 동일한 근본 원인에서 파생된 오류인지 확인한다.
- 독립적인 오류는 각각 재현 조건, 원인, 수정, 검증을 분리한다.
- 첫 번째 수정 후 전체 검증을 다시 실행하여 오류 목록이 변했는지 확인한다.
- 오류를 우선순위로 정렬한다.
  1. 데이터 손상·보안·금전적 영향
  2. 앱 실행 불가·빌드 실패
  3. 핵심 사용자 흐름 중단
  4. 잘못된 표시·경고·성능 저하
  5. 사소한 로그·스타일 문제
- 서로 다른 원인을 한 번의 대규모 변경으로 동시에 고치지 않는다.
- 오류 A 수정으로 오류 B가 가려졌을 가능성을 확인한다.
- 모든 오류를 해결하지 못하면 해결된 항목과 남은 항목을 명확히 구분한다.

## 사용자와 협업하는 통보 방식

작업 중 다음 시점에 짧고 구체적으로 알린다.

### 시작 통보

- 무엇을 재현하고 어떤 범위를 조사하는지 알린다.
- 필요한 경우 사용자가 제공해야 할 정보와 실행 방법을 요청한다.

예시:

> 오류를 먼저 동일한 입력으로 재현하고, API 경계와 상태 변환 로그를 확인하겠습니다. 재현 결과에 따라 수정 범위를 최소화하겠습니다.

### 발견 통보

- 확인된 사실과 아직 가설인 내용을 구분한다.
- 관련 파일과 코드 위치를 함께 알린다.

예시:

> 현재 오류는 `response.data`가 비어 있을 때 변환 단계에서 발생하는 것으로 확인했습니다. 다만 비어 있는 응답의 원인이 API 응답인지 Store 캐시인지 추가로 분리해 검증하겠습니다.

### 수정 전 통보

- 어떤 원인을 어떤 방식으로 수정할지 설명한다.
- 영향 범위와 수정하지 않을 범위를 명시한다.

예시:

> 변환 함수의 빈 응답 처리만 수정하고, API 호출 방식과 다른 화면의 상태 구조는 변경하지 않겠습니다. 수정 후 정상 응답과 빈 응답을 모두 재검증하겠습니다.

### 막힘·위험 통보

- 재현 불가, 외부 서비스 장애, 권한 부족, 불충분한 입력을 즉시 알린다.
- 근거 없이 해결되었다고 주장하지 않는다.

예시:

> 현재는 오류가 재현되지 않아 코드를 추측 수정하지 않았습니다. 재현 시각과 console의 stack trace가 있으면 원인을 더 좁힐 수 있습니다.

### 완료 통보

최종 보고에는 다음만 포함한다.

- 원인
- 수정한 파일과 핵심 변경
- 검증한 시나리오와 결과
- 실행하지 못한 검증과 그 이유
- 남은 위험 또는 사용자에게 필요한 후속 조치

## 회귀 방지 체크리스트

- [ ] 기존 사용자 변경 사항을 보존했는가?
- [ ] 오류를 재현하거나 재현 불가 상태를 명시했는가?
- [ ] 원인과 증상을 구분했는가?
- [ ] 수정 범위가 최소한인가?
- [ ] 다른 호출부와 타입 계약을 확인했는가?
- [ ] 정상·경계·실패 경로를 모두 검증했는가?
- [ ] 수정 후 전체 관련 테스트 또는 빌드를 실행했는가?
- [ ] 새 console 오류와 warning이 없는가?
- [ ] 임시 로그와 민감정보 노출이 없는가?
- [ ] 의도하지 않은 파일 변경이 없는가?
- [ ] 해결하지 못한 오류와 불확실성을 사용자에게 알렸는가?

## 금지 사항

- 오류 메시지를 숨기기 위한 빈 `catch` 또는 무조건 성공 응답
- 원인 확인 없이 임의의 fallback 데이터 삽입
- 테스트를 통과시키기 위한 테스트 삭제·약화·mock 남용
- `any` 또는 lint 비활성화로 타입·정적 오류 은폐
- 무분별한 retry, timeout, sleep으로 비동기 오류 은폐
- 디버깅 로그에 비밀정보와 개인정보 출력
- 사용자 승인 없이 파일·브랜치·커밋을 파괴적으로 되돌리기
- 하나의 오류를 고치면서 관련 없는 리팩터링을 함께 수행하기
- 검증하지 않은 수정 결과를 완료된 것으로 보고하기
